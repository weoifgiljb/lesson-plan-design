## 摘要

**一句话**：本项目把源码交给 GitHub 跨端，却把「让项目真正跑起来的本机资产」留在了上一台电脑——24 个技能配置与 `data/` 下的平台业务数据都不在版本库里，换机后 clone 只能得到一套空壳。

**反向新闻稿**：2027 年 3 月，答辩前一周，作者的笔记本突然无法开机。换机后，他执行四条命令：装回 24 个技能、恢复最近一次数据快照、跑一遍体检、启动平台。30 分钟后，教案库、审查记录、审计台账与演示环境全部回来，答辩照常进行。整个恢复过程没有手工复制数据库，也没有从聊天记录里翻找配置。

**最该先做的五件事（P0）**

- OPS-01 配置清单与技能重建：按 `skills.lock.json` 的固定提交，一条命令装回 24 个技能，带校验、可回滚。
- OPS-02 数据快照备份：SQLite 在线备份 + 教案文件 + 导出物 + 清单，不靠停服复制。
- OPS-03 快照校验与恢复：先校验哈希与结构，再原子恢复；坏了不覆盖、不半写。
- OPS-04 空库防呆：有实例标记而库缺失时，不再静默建空库；健康检查直接报 `data=missing`。
- OPS-05 跨端迁移手册：把「换一台电脑」写成可照做的 8 步，含回滚与验收命令。

**预期结果**：新设备从 clone 到可演示 ≤30 分钟；恢复后 16 张表行数与文件哈希 100% 一致；静默空库 0 次；损坏快照 0 次被接受；答辩前恢复演练连续 3 次通过。

**MVP 范围**：技能重建、备份、恢复、启动防呆、迁移手册（OPS-01 至 OPS-05）。体检、自动备份、管理端 UI 放在 P1/P2，可裁剪。

**阅读指引**：只看结论读本节；要理解为什么丢读第 2 节；要排期读第 3、8 节；要验收读第 7 节与附录 B。

## 1 文档说明

### 1.1 编写目的

插件端与平台端的主体功能已经落地到 v1.2.0，但「一个人、两台设备、一个 GitHub 仓库」的真实使用方式没有被当成需求对待。当前文档假设读者已经装好技能、已经有数据；一旦换机、重装或误删，项目就退化成一套只能看代码、不能演示的空壳。

本文把这类失败从「运维意外」提升为可验收的产品需求：哪些本机资产必须可重建，哪些数据必须可备份与恢复，系统在数据缺失时应该如何表现，跨端迁移的最小操作集是什么。文档同时回答三个问题：这次 bug 的根因是什么；修到什么程度算修好；用什么证据证明修好。

### 1.2 范围与边界

覆盖范围：Agent 侧技能与配置清单；平台侧 `data/` 数据目录；备份、恢复、启动防呆、健康检查、迁移手册与验收测试。

不在范围内：云同步与实时双写；把 `data/` 提交到 Git；P0 阶段的备份加密；跨校多租户与计费；自动冲突合并；平台端在线富文本编辑。

一条关键边界：**本文件不是 BS-04 双端同步的替代**。BS-04 解决「教案在插件端与平台端之间怎么传」；本文件解决「同一台机器的本机资产怎么在设备之间搬」。两者共用契约与哈希口径，但不互相覆盖。

另一条边界：DSH 用户级 profile（`~/.dsh`）、Cursor/Claude Code 等宿主的全局插件目录不在本文件范围；本文件只覆盖仓库内 `.dsh/skills` 与平台 `data/`，其余宿主目录由 OPS-05 手册单独说明。

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 本机资产 | 不入 Git、但项目运行必需的本地状态：`.dsh/skills/`、`data/`、本机环境配置 |
| 跨端 | 从一台设备换到另一台设备，或用 GitHub 仓库在新设备重建工作区 |
| 配置清单 | `docs/dev/skills.lock.json`：技能来源仓库、固定提交、目录与许可 |
| 数据快照 | 一次备份产出的目录或 zip：数据库副本 + 文件副本 + `manifest.json` |
| manifest | 快照清单，记录格式版本、结构版本、文件哈希、表行数与完整性结论 |
| 实例标记 | `data/.instance.json`：证明该数据目录已被本项目初始化过，用于区分首装与丢失 |
| 静默空库 | 数据目录或数据库缺失时，程序不提示、直接新建一个空库并继续服务 |
| WAL | SQLite 的预写日志模式；未 checkpoint 时直接复制 `.db` 可能得到不完整副本 |
| 技能锁 | 以 commit 固定第三方技能版本，避免上游推送悄悄改变运行内容 |

### 1.4 编制依据

`docs/dev/skills.md` 与 `docs/dev/skills.lock.json` 的技能安装与来源记录；`.gitignore` 的忽略规则；`src/backend/app/config.py` 的数据目录定义；`src/backend/app/adapters/db/connection.py` 的建库逻辑；`src/backend/app/main.py` 的启动装配；`src/backend/app/application/health_service.py` 的健康检查；`scripts/repair_schema.py` 的备份实现；`docs/requirements/功能优化需求-BS平台端.md` 的 BS-14；本机 `data/` 目录的实际内容与 `data/files/samples` 的 15 份样例。

|---|---|---|
| 作者（学生） | 需求编写、脚本实现、测试执行、数据整理 | 单人项目，同时承担开发与测试 |

## 2 现状与问题

### 2.1 现象

| 编号 | 现象 | 观测方式 |
|---|---|---|
| S1 | 新设备 clone 仓库后，`docs/dev/skills.md` 记载的 24 个技能不可用 | 目录核查：工作区不存在 `.dsh/skills` |
| S2 | 换机或误删 `data/` 后，平台能正常启动，但教案、任务、审查、审计全部为空，看起来像「刚装好」 | 代码路径核查：缺库即建库 |
| S3 | 答辩或交接前没有官方备份入口，只能手工复制 `data/`，不确定是否完整 | 脚本与页面核查 |
| S4 | 技能安装与升级靠手工下载、复制，漏一个目录、版本不一致都没有提示 | `docs/dev/skills.md` 的升级章节 |
| S5 | 数据缺失时健康检查仍可能显示数据库正常（因为已经新建了一个空库） | `health_service.py` 只查连接与磁盘 |

### 2.2 问题框定

| 维度 | 现状 |
|---|---|
| 谁在痛 | 换设备的作者、答辩前需要证据的导师与评审组、接手项目的下一届 |
| 痛在哪 | 源码在、配置不在；页面在、数据不在；出错时没有提示，只有「怎么空了」 |
| 损失是什么 | 教案与审查证据不可恢复；答辩演示不可用；交接需要重新摸索一遍 |
| 现在的替代 | 手工复制 `data/`、手工装技能、凭记忆补配置；不可验证、不可回滚 |
| 不修的后果 | 每一次换机都是一次赌博；论文的「可复现」承诺不成立 |

### 2.3 根因

| 编号 | 根因 | 证据 | 后果 |
|---|---|---|---|
| R1 | `.dsh/` 被 Git 忽略，24 个技能不在版本库 | `.gitignore:9`；`docs/dev/skills.md:5` | clone 后技能消失 |
| R2 | `data/` 与 `*.db` 被 Git 忽略，业务数据不在版本库 | `.gitignore:12-13`；`config.py:8-9` | 换机后数据为空 |
| R3 | 数据目录缺失时先 `mkdir`，`user_version=0` 时直接执行 schema 建空库 | `connection.py:19,43-48` | 静默空库，掩盖丢失 |
| R4 | 启动阶段只记录数据库异常，不区分「首次安装」与「原有数据丢失」 | `main.py:46-51` | 页面表现为正常新装 |
| R5 | BS-14「备份与迁移」是 P2 且平台端未建设 | `功能优化需求-BS平台端.md:475-485` | 没有官方备份/恢复能力 |
| R6 | 现有备份只在 `repair_schema.py --apply` 修复前顺带执行 | `repair_schema.py:79-83` | 不能用于日常备份与恢复 |
| R7 | 双端同步只覆盖教案事件，不含用户、任务、样例、审计、设置 | `sync_service.py:31-39` | 不能当全量迁移用 |
| R8 | 技能安装/升级是手工 `curl` + `Copy-Item`，无清单校验与回滚 | `docs/dev/skills.md:144-179` | 漏装、版本漂移、无法复现 |

补充观察：当前工作区 `.dsh/skills` 实际不存在，而 `docs/dev/skills.md` 仍按「已装 24 个技能」描述。这说明「文档说装了、机器上没有」已经在真实环境发生，不是假设风险。

### 2.4 影响面

| 资产 | 位置 | 是否入 Git | 丢失后果 |
|---|---|---|---|
| 技能与配置 | `.dsh/skills/`（24 个） | 否 | 产品、测试、后端技能全部不可用，Agent 能力退化 |
| SQLite 库 | `data/app.db`（16 张表） | 否 | 用户、任务、教案、审查、审计、同步游标全空 |
| 教案版本文件 | `data/files/plans/` | 否 | 历史版本正文与报告快照丢失 |
| 样例文件 | `data/files/samples/`（本机 15 份） | 否 | 样例库为空，打分与对照失效 |
| 导出产物 | `data/exports/` | 否 | 已生成的 DOCX 丢失，需重跑导出 |
| 密钥与口令 | `LPP_JWT_SECRET`、用户口令哈希 | 不应入 Git | 泄露风险；恢复后需重设或轮换 |
| 同步断点 | `sync_event` 表 | 否 | 客户端增量拉取的游标丢失 |

| 能力 | 现有实现 | 缺口 |

## 3 目标与成功度量

### 3.1 目标陈述

把「跨端靠记忆、恢复靠运气」改造成「配置可重建、数据可恢复、失败可解释、过程可验收」：任何一台新设备，只要拿到仓库与一份合法快照，就能在 30 分钟内回到可演示状态；任何一次数据缺失，都不会被静默伪装成首次安装。

### 3.2 SMART KR

| 编号 | 指标 | 基线（2026-11-15） | 目标值 | 测量方式 |
|---|---|---|---|---|
| KR1 | 新设备技能重建 | 手工复制 24 个目录，无校验 | `--check` 24/24；联网 ≤10 分钟，离线缓存 ≤2 分钟 | 临时目录演练 + 清单比对 |
| KR2 | 端到端恢复演练 | 不可达 | 备份→删 `data/`→恢复 ≤30 分钟，连续 3 次通过 | 演练记录与计时 |
| KR3 | 恢复一致性 | 无校验 | 16 张表行数与 manifest 完全一致；文件 SHA-256 100% 匹配；`integrity_check=ok` | 恢复脚本输出 + 抽查 |
| KR4 | 空库防呆 | 静默建空库 | 有标记而库缺失时静默建库 0 次；`/health` 单次请求给出 `data=missing` 与修复命令 | 故障注入测试 |
| KR5 | 新设备到可演示 | 实际不可达 | ≤30 分钟（clone→技能→恢复→体检→演示） | 换机演练 |
| KR6 | 失败可解释 | 异常中断或半写 | 中文/空格路径、只读目录、磁盘不足、损坏快照均有非零退出码，且不部分写入 | 负向用例 |

### 3.3 非目标

- 不做数据实时双写、异地容灾与自动故障切换。
- 不把 `data/` 或第三方技能内容提交到 Git。
- P0 不做备份加密；先用操作系统磁盘加密或压缩包口令过渡，加密列为 P2 评估项。
- 不做自动冲突合并；恢复是「覆盖到某个时间点」，不是「多端合并」。
- 不改变 BS-04 的同步语义与契约。

## 5 价值主张与方案取舍

### 5.1 一句话价值

对教师，换机不丢课；对导师与评审，证据随时在；对作者，30 分钟开工；对维护者，失败能解释、操作可回滚。

### 5.2 方案取舍

| 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| D1 数据是否入 Git | 不入 Git，用快照迁移 | 体积、隐私、二进制冲突、WAL 一致性都不适合 Git | 把 `data/` 提交仓库 |
| D2 数据库怎么备 | SQLite 在线备份 API | WAL 未 checkpoint 时直接复制文件可能得到空壳或半套 | 停服后复制 `.db` |
| D3 技能怎么跨端 | 按 `skills.lock.json` 固定提交重建 | 第三方内容有许可与体积问题，锁提交可复现 | 把 `.dsh/skills` 提交仓库 |
| D4 先做哪一层 | P0 只做 CLI + 启动防呆 + 手册 | 单人项目，先把「能恢复」做实，UI 后置 | 先做管理端页面 |
| D5 是否做云同步 | 不做 | 超出毕设范围，且解决不了单机数据丢失 | 网盘实时同步 |
| D6 恢复语义 | 覆盖到某个时间点，不自动合并 | 教学设计没有可靠自动合并语义 | 多端自动合并 |

### 5.3 价值曲线

| 维度 | 现状 | 目标 |
|---|---|---|
| 配置可重建 | 手工、无校验 | 一条命令、24/24 可核对 |
| 数据可恢复 | 不可达 | 快照 + 校验 + 回滚 |
| 失败可解释 | 静默空库 | 明确状态与修复命令 |
| 证据可审计 | 无恢复记录 | 恢复报告 + 后续审计 |

**接口与文件**

| 命令 | 用途 | 关键参数 | 退出码 |
|---|---|---|---|
| `bootstrap_skills.py` | 安装/更新全部技能 | `--check`、`--only`、`--cache-dir`、`--json`、`--global` | 0 成功；2 用法错误；3 校验失败；4 来源不可用；5 安装失败已回滚 |

**失败模式**：归档损坏、部分技能缺失、目录被占用、路径含中文或空格、许可文件缺失。任一失败必须回滚到安装前状态，并输出可执行的下一步。

### 6.4 OPS-02 数据快照备份

**状态**：✅ 已完成
**证据**：`scripts/backup_data.py`、`tests/ops/test_backup_restore.py::test_snapshot_manifest_matches_files_and_zip`；SQLite 在线备份、files/exports、manifest 与 zip。
**实现说明**：manifest 记录 16 张表行数、逐文件哈希、`integrity_check`；失败不产出成功快照。

**现状**：没有日常备份；`repair_schema.py` 的备份只在修复前发生，且只覆盖数据库文件。

**目标行为**：新增 `scripts/backup_data.py`，用 SQLite 在线备份 API 复制数据库，连同 `data/files/`、`data/exports/`（可关）写入快照目录或 zip；生成 `manifest.json`；备份完成后对副本做 `PRAGMA integrity_check`、读取 `user_version` 与 16 张表行数；任一步失败不产出「成功」快照。

**快照布局**

| 路径 | 内容 |
|---|---|
| `app.db` | 数据库副本（在线备份，非文件直拷） |
| `files/` | 教案版本文件、样例文件，按原相对路径 |
| `exports/` | 导出 DOCX（`--no-exports` 可排除） |
| `manifest.json` | 格式版本、结构版本、时间、主机标签、逐文件哈希、表行数、完整性结论 |

**manifest 字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `formatVersion` | 整数 | 快照格式版本，当前为 1 |
| `createdAt` | 字符串 | ISO 8601 带时区 |
| `label` | 字符串 | 可选标签，如 `before-defense` |
| `appVersion` | 字符串 | 生成快照的代码版本或提交 |
| `schemaVersion` | 整数 | 数据库 `user_version` |
| `database.sha256` | 字符串 | `app.db` 副本的 SHA-256 |
| `database.rowCounts` | 对象 | 表名到行数，16 张表 |
| `database.integrity` | 字符串 | `ok` 或失败原因 |
| `files[]` | 数组 | 每项含 `path`、`size`、`sha256` |
| `totals` | 对象 | 文件数与总字节数 |

**验收标准**

- 备份一个含教案、样例与导出物的数据目录，manifest 中 16 张表行数与库内一致，逐文件哈希可复算。
- WAL 模式下有并发写时，备份副本 `integrity_check=ok`，不需要停服。
- 源库损坏或缺失时明确失败，退出码 3，不生成可被误认为成功的快照。
- 快照目录与 zip 两种形态内容一致；中文路径与空格路径均可用。

**失败模式**：磁盘不足、文件被占用、WAL 未 checkpoint、导出物超大、权限不足；失败时保留临时目录供排查，不覆盖已有快照。

**影响模块**：`scripts/`、`data/`、`.gitignore`（新增 `/backups/` 建议）、运维文档。

### 6.5 OPS-03 快照校验与恢复

**状态**：✅ 已完成
**证据**：`scripts/restore_data.py`、`tests/ops/test_backup_restore.py`；校验 manifest/哈希/行数，staging 恢复与原子替换。
**实现说明**：篡改快照退出码 3、结构版本过高退出码 4；目标非空需 `--force`，恢复前保留 `.pre-restore-*`。

**现状**：没有恢复能力；直接复制 `data/` 无法判断是否完整，也没有回滚。

**目标行为**：新增 `scripts/restore_data.py`，先校验 manifest 与全部文件哈希，再把快照恢复到 staging 目录，跑数据库迁移与完整性检查，最后原子替换目标数据目录；恢复前自动为当前数据打一次快照；目标非空时必须显式 `--force`；版本高于当前代码支持时拒绝恢复。

**恢复顺序**

| 步骤 | 动作 | 失败时 |
|---|---|---|
| 1 | 校验快照格式版本与 manifest 必填字段 | 退出码 3，目标不变 |
| 2 | 逐文件比对大小与 SHA-256 | 退出码 3，目标不变 |
| 3 | 校验 `schemaVersion` 不高于当前代码 | 退出码 4，目标不变 |
| 4 | 恢复到 staging 目录并跑迁移 | 退出码 5，清理 staging |
| 5 | 对 staging 做完整性与行数比对 | 退出码 5，清理 staging |
| 6 | 备份当前数据，原子替换 | 退出码 5，回滚当前数据 |
| 7 | 输出恢复报告（表行数、文件数、耗时） | 0 |

**验收标准**

- 篡改快照中任意一个字节，恢复被拒绝，退出码 3，现有数据完全不变。
- 快照 `schemaVersion` 高于当前代码，恢复被拒绝，退出码 4，并提示升级代码而不是降级数据。
- 目标目录非空且未加 `--force` 时拒绝执行；加 `--force` 时先自动备份，再恢复。
- 恢复后 16 张表行数与 manifest 一致，文件哈希一致，`/health` 回到 `data=ok`。

**失败模式**：manifest 缺失、文件缺失、哈希不匹配、目标目录被占用、磁盘不足、迁移脚本缺失；所有失败必须回滚或保持原状，不允许半套数据上线。

**影响模块**：`scripts/`、`data/`、`app/adapters/db/connection.py`（只复用初始化）、审计文档。

### 6.6 OPS-04 空库防呆与健康检查

**状态**：✅ 已完成
**证据**：`src/backend/app/adapters/db/instance.py`、`app/adapters/db/connection.py`、`app/main.py`、`app/api/routers/health.py`、`src/backend/tests/test_health.py::TestInstanceStartup`。
**实现说明**：新增 `.instance.json`、`checks.data`、`data=missing/foreign/corrupt` 与 `LPP_ALLOW_INIT=1` 逃生口；有标记无库不建空库。

**现状**：`connect()` 先创建父目录，`initialize()` 在 `user_version=0` 时直接执行 schema；缺库与首装不可区分。

**目标行为**：首次成功初始化后写 `data/.instance.json`；启动时按「标记是否存在、库是否存在、目录是否为空」决定行为；有标记无库时不建库，`/health` 返回 503 与 `data=missing`；只有无标记、无库且目录为空才允许首次初始化；提供 `LPP_ALLOW_INIT=1` 作为测试与显式重建的逃生口。

**启动决策**

| 实例标记 | 数据库 | 行为 |
|---|---|---|
| 无 | 无，数据目录为空 | 首次安装：建库、写标记、正常启动 |
| 无 | 无，数据目录非空 | 判定 `foreign`：不建库，`/health` 503，要求人工确认或恢复 |
| 无 | 有 | 兼容旧数据：补写标记，正常启动 |
| 有 | 有 | 正常启动 |
| 有 | 无 | 判定数据丢失：不建库，`/health` 503，返回修复命令 |
| 有 | 有但损坏 | 启动失败，`/health` 报数据库不可用，提示恢复 |

**健康检查扩展**

| 字段 | 说明 |
|---|---|
| `checks.data` | `ok`、`missing`（有标记无库）、`foreign`（无标记、无库但目录非空，疑似从别处拷来） |
| `data.dir` | 数据目录的相对路径，不返回本机绝对路径 |
| `data.db` | 数据库文件名 |
| `data.schemaVersion` | 当前库结构版本 |
| `data.instanceId` | 实例标记中的 UUID |
| `data.lastBackupAt` | 最近一次成功备份时间，未备份为 `null` |
| `data.rowCounts` | 关键表行数摘要，用于人工核对 |

**验收标准**

- 删除 `data/app.db` 但保留标记，启动后不产生新库，`/health` 返回 503 且 `checks.data=missing`，响应含恢复命令。
- 全新空目录启动，正常建库并写标记，`/health` 为 `data=ok`。
- 设置 `LPP_ALLOW_INIT=1` 时允许显式重建，日志记录该行为。
- 健康响应不泄露本机绝对路径与密钥。

**失败模式**：标记文件损坏、数据目录只读、标记与库同时被删除（退化为首装，文档必须说明该边界）、并发启动。

**影响模块**：`app/config.py`、`app/adapters/db/connection.py`、`app/main.py`、`app/application/health_service.py`、`app/api/routers/health.py`、契约快照。

### 6.12 安全与隐私

- 快照包含教师数据与用户口令哈希，属于敏感文件：不得提交 Git、不得放入公开网盘、不得在日志中打印内容；建议存放在受控目录或加密盘。
- manifest 只记录哈希与行数，不记录教案正文、口令、令牌。
- 技能重建只读 `skills.lock.json`，不写入任何凭据；`--global` 必须显式开启。
- `LPP_ALLOW_INIT=1` 是危险开关，只用于测试与显式重建，日志必须留痕。
- P0 不做备份加密；在文档中明确建议使用 BitLocker 或 7z 口令作为过渡，加密列为 P2 评估项。

### 6.13 失败模式

| 场景 | 表现 | 要求 |
|---|---|---|
| 网络不可用 | 技能下载失败 | 退出码 4，提示离线缓存，不产生半套目录 |
| 归档损坏 | 解压或校验失败 | 回滚，已安装技能不变 |
| 磁盘不足 | 写快照中途失败 | 不产出成功快照，保留临时目录 |
| WAL 未 checkpoint | 直接复制得到空壳 | 必须使用在线备份 API |
| 并发写 | 备份过程中有新事务 | 在线备份一致性通过，不要求停服 |
| 中文/空格路径 | 命令找不到文件 | 全部路径使用参数传递，测试覆盖 |
| 只读目录 | 安装或恢复失败 | 明确权限错误与目标路径 |
| 版本超前 | 快照结构版本高于代码 | 退出码 4，拒绝恢复 |
| 快照被篡改 | 哈希不匹配 | 退出码 3，目标不变 |
| 标记与库同时删除 | 退化为首装 | 文档说明无法区分，建议定期备份 |
| 恢复到非空目录 | 误覆盖 | 默认拒绝，`--force` 且先自动备份 |
| 恢复中断 | 半套数据 | staging + 原子替换 + 回滚 |

## 9 风险与未决项

### 9.1 pre-mortem

| 风险 | 影响 | 应对 |
|---|---|---|
| GitHub/codeload 网络不可用（老虎） | 技能装不回 | 离线缓存 + 可复制的缓存目录 + 失败提示 |
| WAL 一致性（老虎） | 备份是空壳 | 强制使用在线备份 API，备份后 `integrity_check` |
| 中文路径与权限（老虎） | 命令在真实机器失败 | 参数化路径 + T-11/T-12 负向用例 |
| 结构版本漂移（老虎） | 恢复后库结构不兼容 | manifest 记录 `schemaVersion`，超前拒绝、落后迁移 |
| 备份体积（纸老虎） | 占磁盘 | 排除 `exports/` 开关 + 保留策略 |
| 单人项目排期（纸老虎） | P1/P2 延期 | P0 先闭环，P1/P2 可裁剪 |
| 备份含隐私数据（大象） | 泄露风险 | 不入 Git、受控存放、加密列为 P2 |
| 把恢复当合并（大象） | 覆盖他人改动 | 文档明确「覆盖到时间点」，冲突交给人 |
| 标记与库同时删除（大象） | 退化为首装 | 文档说明边界，靠定期备份兜底 |

### 9.2 待确认

1. 快照存放位置与保留周期：仅本机、U 盘，还是私有网盘。
2. 是否在 P0 就引入备份加密，还是先用 BitLocker/7z 过渡。
3. 管理端备份/恢复是否进入本轮答辩范围，还是只做 CLI。
4. 是否把 OPS 组补进 LPP-OWN-001 并重算需求总数（当前为 34 条）。
5. 答辩演示机是否固定，是否需要在演示前自动执行一次备份。
