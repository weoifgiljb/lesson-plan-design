## 摘要

**一句话**：平台端不是第二个生成器，而是**契约复校器 + 证据台账 + 管理与统计视图**。它的第一职责不是"存下来"，而是"不信任客户端结论：入库前重算哈希、重跑校验、重核报告"。

**最该先做的六件事（P0）**

- BS-01 契约复校入库：任何数据只有一条写入口，篡改、过期、缺证据的包一律拒收。
- BS-02 教案库与不可变版本：每次入库生成新版本，旧版本可查不可改，差异可读。
- BS-03 审查中心与证据链：问题、轮次、放行、审校方式一屏可查，缺证据标红。
- BS-04 双端同步与冲突：以 `baseHash` 做乐观锁，冲突返回 409，不做自动合并。
- BS-05 角色权限与会话：教师、教研组长、管理员三角色，越权 0。
- BS-06 审计台账：登录、入库、导出、放行、删除全部留痕，只追加不删除。

**预期结果**：双端数据一致率 ≥98%，证据链完整率 100%，入库篡改拦截 100%，平台任务完成率 ≥90%，SUS ≥70，结构合规率 ≥95%，闭环缺陷密度 ≤0.5。

**MVP 范围**：登录、任务与建课、教案库、审查中心、导出中心、统计看板、样例库、审计。平台端 v1.0 只做"看、收、审、导、统"，不做在线富文本编辑。

**阅读指引**：先读第 3 节契约，再看第 4 节需求；页面与接口在第 5 节；测试与验收在第 7 节；与插件端 18 条需求的对应关系见附录 A。

## 1 文档说明

### 1.1 编写目的

双端开题报告把平台端概括为"教案库、样例库、审查中心、导出中心、统计与角色权限"，但这句话不足以指导实现，也不足以验收。本文档把它展开为 16 条可判定的功能需求，并与插件端 18 条优化需求配对，说明平台端**必须校验什么、必须拒绝什么、必须留下什么证据**。

文档同时回答三个问题：平台端与插件端的边界在哪里；两端用什么契约衔接；2027 年 2—3 月实现完成后，用什么用例证明它成立。

### 1.2 范围与边界

覆盖范围：浏览器端页面、服务端接口、数据模型、同步与冲突、角色权限、审计、统计、部署与测试。

不在范围内：教案生成算法（仍在插件端）；在线富文本编辑（平台端 v1.0 只读展示，修订在插件端完成后作为新版本上传）；与学校教务系统的对接；学生个人信息；跨校多租户与计费。

一条关键边界：**平台端不复用插件端的"结论"，只复用插件端的"代码"**。平台不会因为上传的报告写着 `passed` 就放行，而是用固定版本的 `validate.py` 重新算一遍；平台也不重写 Word 版式，而是调用固定版本的 `export_docx.py`。这条边界决定了后面所有需求。

### 1.3 与插件端需求的关系

插件端需求（FR-01 至 FR-18）是平台端输入的质量前提，二者不是并列关系：

- 平台端的入库复校必须使用与插件端相同的规则版本（`ruleVersion`），否则同一份教案会出现"本地过、平台不过"。
- 插件端 FR-03、FR-05 把门禁状态机与证据快照补严之后，平台端才能按状态机校验；在此之前，平台端对历史数据采用"入库但标记 `legacy`"的迁移策略，不阻断教师既有教案。
- 插件端 FR-06 增加审校独立性字段后，平台端统计才能区分独立子代理与角色模拟。
- 插件端 FR-11 的版本化导出与 FR-13 的样例库同步，直接决定平台端导出中心与样例库的上限。

两边需求的完整映射见附录 A；实现顺序上，建议插件端 P0（FR-01/03/05/07/08）先于平台端入库复校上线。

### 1.4 术语与缩写

| 术语 | 含义 |
|---|---|
| 契约包 | 一次同步提交的 zip：`manifest.json` + 教案 JSON + 审查报告 + 可选 DOCX + 媒体文件 |
| planHash | 教案内容的规范化 SHA-256，算法与插件端 `lib.py` 完全一致 |
| baseHash | 客户端上传时声明"我基于哪一版修改"，用于乐观锁 |
| engineVersion | 平台端执行校验、导出所用的插件端脚本版本（commit 或语义版本） |
| 证据链 | 哈希匹配、轮次连续、问题状态、放行记录、审校方式五者齐全 |
| 双端一致率 | 同步记录中教案、报告、哈希三者与插件端一致的占比 |
| 幂等键 | 同一契约包重复提交时用于去重的键，取 `planHash + reportHash` |

## 2 平台端定位与总体设计

### 2.1 设计原则

写平台端需求时先定五条原则，后面的功能都是从这五条推出来的：

1. **先契约后页面**：页面可以改，契约不能悄悄改；契约版本化，升级走白名单与迁移。
2. **平台端不做第二套生成**：不重写校验、审查、版式；调用插件端脚本并记录 `engineVersion`，避免两端逻辑分叉。
3. **入库管道是唯一写入口**：教师端不能直接改库；手动导入与同步推送都走同一复校管道，通过后才落库。
4. **冲突不自动合并**：教学设计没有可靠的自动合并语义，冲突交给人，系统只负责把差异摆清楚。
5. **指标带分母、证据可复核**：统计页面必须显示分子与分母，任何"合规率"都能点回原始记录。

### 2.2 双端职责边界

| 能力 | 插件/技能端 | 平台端 |
|---|---|---|
| 教案生成 | 在宿主中起草、检索样例、填写 JSON | 下发任务、选择样例、查看草稿 |
| 结构校验 | 本地 `validate.py`，退出码判定 | 入库前用同一规则版本复校并记录 |
| 对抗审查 | 独立审校、哈希绑定报告、教师实名放行 | 只读展示问题、轮次、放行与审校方式 |
| Word 导出 | 本地 `export_docx.py` | 导出中心批量调用同一引擎，记录产物哈希 |
| 知识资产 | 读取 schema 与 examples | 维护样例库、截图资产与版本 |
| 管理与统计 | 无 | 教案库、角色权限、审计、合规率与缺陷统计 |
| 运行环境 | Cursor、Claude Code、Codex、Qoder、CodeBuddy、飞书 | 浏览器，校内 B/S 部署 |

### 2.3 总体架构

平台端采用前后端分离：前端 Vue 3 与组件库，负责登录、任务、教案库、审查中心、导出中心与统计；后端建议 Python Web 框架（FastAPI 或 Flask），与插件端脚本同语言，直接 import `lib.py`、`export_docx.py`，不复制算法；SQLite（WAL 模式）保存元数据、版本与审计；文件存储保存教案 JSON、审查报告、DOCX 与媒体；同步通道提供 REST 与共享目录两种方式；部署在校内单机或教研组电脑，经反向代理提供 HTTPS。

后端"同语言"不是形式要求，而是为了复用 `plan_hash` 的规范化 JSON 与 `validate_plan` 的判定，避免出现两套哈希、两套规则。若未来改用其他语言，必须通过第 3.6 节的跨语言黄金测试。

### 2.4 四条核心流程

**A 入库**：上传契约包 → 校验 manifest 与文件哈希 → 解析并检查版本白名单 → 服务端重算 `planHash` → 用固定 `engineVersion` 重跑结构校验 → 核对报告哈希、轮次、状态、放行 → 权限与归属校验 → 幂等判定 → 写入新版本与审计 → 返回结果。

**B 审查查看**：审查列表 → 详情（findings、overrides、repairHistory、reviewer）→ 证据链完整度面板 → 导出问题清单。

**C 批量导出**：选择版本 → 门禁判定 → 调用固定 `engineVersion` 的导出脚本 → 保存 DOCX 与 SHA-256 → 打包下载 → 记录导出日志。

**D 统计**：按口径聚合 → 展示分子分母与筛选条件 → 支持下钻到记录 → 导出 CSV。

## 3 数据契约

契约是平台端的第一等公民。这一节先于页面与接口，因为页面可以重做，契约一旦分叉，两端的教案就无法互认。

### 3.1 教案 JSON

沿用插件端 `references/schema.md` 的 17 个必填字段：学校、学年、学期、课程、教研组、周次、课次、教学内容标题、计划学时、教学目的、知识目标、能力目标、素质目标、重点难点、教学方法、教学资源、八步流程。可选字段：教案编号、任课教师、教学对象、授课日期、内容补充、媒体资产。

八步流程键名固定，教学反思可为空；工作任务实施须包含"必须完成/必做"；结构化活动行须有 `mainContent`，建议带 `studentActivity`、`minutes`、`evidence`。版本字段：审查报告与同步包 `manifest.json` 中的 `schemaVersion` 当前为 1；教案 JSON 本体不带版本字段，`planHash` 按原样 JSON 计算。

### 3.2 审查报告

报告字段：`schemaVersion`、`rubricVersion`、`toolVersion`、`planHash`、`planSnapshot`、`round`、`duplicateReview`、`reviewer`、`reviewedAt`、`structuralValidation`、`findings`、`overrides`、`repairHistory`、`attestation`、`status`、`conclusion`。

状态集合：`structure_invalid`、`pending_reviewer`、`needs_repair`、`passed`、`passed_with_override`、`passed_with_accepted_minor`。一轮最多一条 finding；`blocker` 与 `major` 未关闭时必须修复或教师实名放行；`minor` 未接受时阻断导出，接受记录写入 `overrides`（`kind=minor_acceptance`）；`passed` 必须带 `no_counterexample` 声明。`round` 必须等于上一轮加一，首轮为 1；同一 `planHash` 的重复审校写入 `duplicateReview=true`；`planSnapshot` 保存被审教案，供离线复核。

平台端只读报告，不修改报告；需要放行时，教师在插件端完成并重新上传报告，平台端以新版本接收。

### 3.3 planHash 规范

`planHash` 必须是教案对象的规范化 JSON 的 SHA-256：

- 键排序（`sort_keys=True`）；
- 紧凑分隔符（`,` 与 `:`，无空格）；
- 不转义中文（`ensure_ascii=False`）；
- UTF-8 编码后取 SHA-256 十六进制小写。

任何字段变化都会导致哈希变化；仅调整键顺序或等价的 Unicode 表示不应改变哈希。平台端在入库时独立重算，不采信 manifest 或报告里写的值。跨语言实现必须用插件端 15 份样例做黄金对照，逐份比对哈希。

### 3.4 同步包

契约包是一个 zip，目录结构固定：

- `manifest.json`：`contractVersion`、`planHash`、`reportHash`、`schemaVersion`、`rubricVersion`、`createdAt`、`files[]`（每项含 `path`、`sha256`、`size`）。
- `plan.json`：教案本体。
- `plan.review.json`：审查报告。
- `lesson.docx`：可选，插件端已导出时携带。
- `media/`：可选，教材截图，路径必须相对且不含 `..`。

平台端先验 manifest 里每个文件的 SHA-256，再独立重算 `planHash`；两者不一致按篡改处理。媒体缺失或哈希不符一律拒收，不做"先入库后补图"。zip 条目不得包含 `..`、绝对路径或符号链接，负例见 `tests/fixtures/dual-end/platform/packages/zip-slip.zip`。

### 3.5 版本与兼容

三个版本字段共同决定能否接收：`schemaVersion`（教案结构版本，随审查报告与 manifest 传递）、`rubricVersion`（审查量规）、`engineVersion`（平台执行校验/导出所用脚本版本）。平台端维护白名单，收到未知版本返回 422 并列出支持版本；升级时先跑迁移脚本，再切换白名单。

历史数据不因规则升级被改写：旧版本保持原样并标注 `legacy`，新版本按新规则校验，统计时分开计数。

### 3.6 契约测试

平台端必须自带一组黄金契约测试：7 份信息技术金标准 + 8 份 C 语言样例，逐份验证解析、`planHash`、结构校验结论、报告字段。再增加三类负例：篡改任意字段（哈希必须变）、仅调整键顺序（哈希必须不变）、把中文写成 `\u` 转义（解析后哈希必须不变）。这组测试同时作为插件端与平台端的"共同语言"。

### 4.1 P0 需求

#### BS-01 契约复校入库

**现状**：平台端未建设；插件端已能产出教案 JSON、审查报告与 DOCX；`planHash` 与结构校验逻辑已存在于 `lib.py`。

**目标行为**：提供统一入库管道，手动入口为 `POST /api/v1/plans/import`，与 `POST /api/v1/sync/push` 共用同一复校逻辑；服务端验 manifest、重算 `planHash`、用固定 `engineVersion` 重跑结构校验、核对报告一致性、校验媒体、判幂等，全部通过才落库；拒绝时给出稳定错误码与可定位原因。

**验收标准**

- 篡改教案任一字段后上传，返回 422 `HASH_MISMATCH`，数据库无新版本，审计记录拒绝原因。
- 报告声称结构通过但服务端复校失败，返回 422 `STRUCTURE_INVALID`，并附 issue 列表。
- 同一契约包重复上传返回 200 与既有 `versionNo`，不新增版本。
- `schemaVersion` 或 `rubricVersion` 不在白名单时返回 422，响应列出支持版本。
- 媒体缺失或哈希不符返回 422，响应逐个列出缺失文件。
- 正常包返回 201，含 `planId`、`versionNo`、`reviewId`、`planHash`，审计含操作者与 `traceId`。

**功能测试要点**

- 负例矩阵：篡改字段、改哈希、删媒体、换版本号、报告轮次回退、waived 无放行、zip 路径穿越。
- 幂等：同包连续提交 3 次、并发提交 2 次。
- 编码：中文路径、空格路径、大文件（单包 50 MB）。

**影响模块**：后端导入服务、契约校验、`plan_version` 表、审计。

#### BS-02 教案库与不可变版本

**现状**：平台端未建设；插件端每次修订都会让旧审查报告因哈希不匹配失效，但没有平台侧版本链。

**目标行为**：教案列表按课程、班级、教师、周次、状态筛选；详情展示当前版本、历史版本、审查与导出记录；支持任意两版字段级差异；删除为软删除；管理员无修改教案内容的入口。

**验收标准**

- 每次入库生成新版本，旧版本不可修改；版本号连续递增。
- 差异视图能定位到字段路径与前后值，至少覆盖八步与三维目标。
- 软删除后列表不可见，审计与历史版本仍可查，恢复需管理员操作并留痕。
- 教师只能看到本人教案；组长看本组；管理员看全部；越权访问写审计。

**功能测试要点**

- 版本链：连续 10 次入库、并发入库、回滚（以旧版新建新版）。
- 差异：新增字段、删除字段、长文本、结构化活动数组。
- 权限：横向越权读取他人教案。

**影响模块**：教案库页面、版本服务、`plan`/`plan_version` 表。

#### BS-03 审查中心与证据链

**现状**：插件端已有审查报告与门禁，但报告只存在教师本机；平台端没有集中查看入口。

**目标行为**：按状态、严重度、教师、时间筛选审查记录；详情展示 findings、overrides、repairHistory、reviewer 与审校方式；提供证据链面板，逐项标记"哈希匹配、轮次连续、放行完整、审校方式合规"，任一项不满足标红并给出原因。

**验收标准**

- 六种报告状态都能正确展示，状态与报告内容一致。
- 证据链完整率可在列表与详情同时看到；不完整记录可导出问题清单。
- 平台端没有修改报告或补录放行的入口；需要补证据时只能回插件端操作后重新上传。
- 同一教案同一轮次出现两条报告时拒绝入库并提示冲突。

**功能测试要点**

- 状态矩阵：`passed`、`passed_with_override`、`passed_with_accepted_minor`、`needs_repair`、`pending_reviewer`、`structure_invalid`。
- 证据缺失：无快照、轮次跳号、waived 无放行、`role_simulation` 未标注。
- 篡改报告：改状态、改哈希、删 findings。

**影响模块**：审查中心页面、`review`/`finding`/`override` 表、证据链计算。

#### BS-04 双端同步与冲突处理

**现状**：插件端可离线运行；平台端未建设；双端一致率目前无法测量。

**目标行为**：提供 REST 推送与拉取，另支持共享目录监听；推送与手动导入共用同一复校管道；上传时携带 `baseHash`，服务端以乐观锁判断是否基于当前头版本；冲突返回 409 与服务端头版本、差异摘要；不自动合并；离线队列重连后幂等重试；所有同步写入 `sync_log`。

**验收标准**

- `baseHash` 与服务端头版本不一致时返回 409，响应含服务端 `headVersion` 与差异摘要。
- 同一包重复推送返回 200，不重复入库；断网重试不产生重复版本。
- 拉取支持 `since` 游标，返回增量列表；客户端可按游标续传。
- 冲突解决只有两种动作："以本地为准上传为新版本"或"以平台为准拉取覆盖本地"，两种都留痕。
- 双端一致率可由 `sync_log` 直接计算，口径见第 7 节。

**功能测试要点**

- 离线修改后上传、两端同时修改、连续快速上传、传输中断。
- 时钟偏移、包内文件缺失、manifest 与文件哈希不符。

**影响模块**：同步接口、`sync_log` 表、插件端同步客户端（后续）。

#### BS-05 角色权限与会话

**现状**：平台端未建设；插件端的实名放行目前只记录教师姓名，没有平台账号绑定。

**目标行为**：教师、教研组长、管理员三角色；按"角色 + 资源归属"双重判定；会话使用 HttpOnly、SameSite 的 Cookie；写操作校验 CSRF；登录失败锁定；密码强度与首次改密。

**验收标准**

- 教师访问他人教案返回 403 且写入审计；组长可读本组；管理员可读全部但无教案编辑接口。
- 未登录访问任何业务接口返回 401；越权 403 与未登录 401 可区分。
- 连续 5 次登录失败锁定 10 分钟；锁定事件可在审计中查到。
- 会话固定、CSRF、暴力破解三类用例全部被拦截。

**功能测试要点**

- 角色与接口的全矩阵（3 个角色 × 全部业务接口）。
- 横向越权（改 URL 中的 id）、纵向越权（教师调用管理员接口）。
- 会话：固定、过期、并发登录、退出后重放。

**影响模块**：认证服务、权限拦截器、`user` 表、审计。

#### BS-06 审计台账

**现状**：平台端未建设；插件端只有报告内的 repairHistory，没有跨操作审计。

**统计口径补充（BS-08）**：指标默认只统计未软删除的教案，与列表/导出口径一致；已软删除教案的审计与历史版本仍可查，如需纳入统计应新增显式参数（本期不提供）。分母为 0 时返回 `value=null` 且 `available=false`；分母为 1~4 时额外返回 `sampleInsufficient=true`，前端只显示"样本不足"。单份耗时的起点优先取关联任务的创建时间，没有任务关联的样本回退到教案创建时间，并在 `basis` 里分别计数（`task` / `plan`）。

**目标行为**：登录、入库、导出、查看放行记录、软删除、用户与角色变更、引擎版本切换全部写入审计；字段含操作者、动作、对象、变更前后哈希、时间、IP、`traceId`；审计只追加，不提供修改与删除接口。

**验收标准**

- 每个写操作都能在审计中查到一条记录，且与业务记录一一对应。
- 审计接口只有查询与导出，没有写入、修改、删除方法。
- 可按操作者、动作、时间范围、对象筛选；导出 CSV 含全部字段。
- 审计保留期不少于 1 年，超期归档不删除。

**功能测试要点**

- 覆盖矩阵：每个写接口至少一条审计断言。
- 注入：伪造操作者、篡改时间、重复提交。
- 分页与大数据量导出。

**影响模块**：审计服务、`audit_log` 表、管理员页面。

### 4.2 P1 需求

#### BS-07 导出中心

**现状**：插件端可本地导出 DOCX；平台端没有批量导出与模板管理。

**目标行为**：选择若干教案版本批量导出；每项先过门禁（结构 + 当前报告 + 未关闭问题）；服务端调用固定 `engineVersion` 的 `export_docx.py` 生成 DOCX；保存文件与 SHA-256；逐项返回成功或失败原因；支持打包下载；记录导出日志。

**验收标准**

- 门禁不通过的版本不会进入导出队列，响应给出具体原因。
- 导出记录含 `planHash`、`reportHash`、`engineVersion`、产物 SHA-256。
- 50 份教案批量导出在 5 分钟内完成，单份失败不影响其他项。
- 缺图、模板缺失、磁盘不足三类异常都有明确提示，不产生半成品文件。

**功能测试要点**

- 门禁失败、媒体缺失、并发批量、重复导出、磁盘写满。
- 产物回读：DOCX 含学校、编号、授课日期与页脚版本号（依赖插件端 FR-02/FR-10）。

**影响模块**：导出中心页面、导出队列、`export_job` 表、文件存储。

#### BS-08 统计看板

**现状**：开题报告表 2 定义了 9 个指标，但没有数据来源与计算实现。

**目标行为**：按课程、班级、教师、周次、时间范围聚合 9 个指标：结构合规率、金标准贴近分、闭环缺陷密度、证据链完整率、双端数据一致率、平台任务完成率、专家评分、单份耗时、平台可用性；每个指标展示分子、分母与筛选条件；支持下钻到记录；支持 CSV 导出。其中结构类、缺陷类、一致性类指标由报告与同步日志自动计算，单份耗时由任务创建到导出的时间差计算，专家评分与 SUS 由管理员导入评分表。

**验收标准**

- 每个指标的公式与开题报告表 2 一致，页面同时显示分子与分母。
- 教师只看到本人数据，组长看本组，管理员看全校；越权查询返回 403。
- 空数据、单条数据、跨学期数据均不报错，显示"暂无数据"而非 0 分。
- 统计数字可用同一口径从数据库复算，误差为 0。

**功能测试要点**

- 黄金数据集：手工构造 20 份教案、已知合规率与缺陷密度。
- 边界：0 份、1 份、全部不合格、日期边界。
- 权限：三种角色的查询范围。

**影响模块**：统计服务、聚合视图、图表组件、CSV 导出。

#### BS-09 样例库与资产

**现状**：插件端已有 7 份信息技术金标准在 `examples/`，8 份 C 语言示例在 `output/`；平台端没有样例浏览与上传校验。

**目标行为**：样例按课程、周次、课次、课题检索；展示结构分与有效性；支持预览与下载；管理员上传样例时自动跑结构校验，不合格拒绝；教材截图作为资产挂接样例或教案，记录哈希与说明。

**验收标准**

- 样例库数量与插件端样例目录一致（FR-13 完成后为 15 份），每份标记是否通过校验。
- 不合格样例上传被拒并给出 issue；重复课题提示冲突。
- 下载包可被插件端直接使用，无需二次转换。
- 资产缺失或哈希不符时样例标记为不完整。

**功能测试要点**

- 损坏 JSON、超长文本、重复课题、媒体缺失、批量上传。

**影响模块**：样例库页面、`sample`/`asset` 表、文件存储。

#### BS-10 任务与建课

**现状**：平台端未建设；插件端由教师直接说"第几周第几次"开始。

**目标行为**：教研组或教师创建教学任务（课程、周次、课次、课题、班级、截止时间）；生成任务包（空教案模板、字段说明、最接近样例链接），供插件端直接使用；任务状态随入库、审查、导出自动推进。

**验收标准**

- 任务包导入插件端后结构校验通过，不需要手工补字段。
- 同一课程、周次、课次、班级重复建课时提示冲突，确认后才允许。
- 状态流转正确：待生成 → 待审 → 已通过 → 已导出；回退需人工并留痕。
- 任务列表按截止时间排序，逾期标红。

**功能测试要点**

- 重复任务、跨学期、班级为空、截止时间为过去。
- 状态机全路径与非法跳转。

**影响模块**：任务页面、`task` 表、任务包生成。

#### BS-11 隐私与脱敏

**现状**：教案含学校、班级、教师姓名；插件端本地处理，平台端集中存储后风险上升。

**目标行为**：不采集学生姓名与学号；班级只用于归属与筛选；跨教师统计按最小聚合展示；导出文件署名任课教师；提供数据保留期与删除申请流程；日志不记录教案全文。

**验收标准**

- 数据库与接口字段白名单中不存在学生个人信息字段。
- 跨教师统计在样本小于 5 时只显示"样本不足"，不显示明细。
- 删除申请在 7 个工作日内处理，删除为软删除并保留审计。
- 日志脱敏：不出现教案全文、密码、会话令牌。

**功能测试要点**

- 字段扫描、接口响应检查、统计小样本、日志抽样。

**影响模块**：数据模型、统计聚合、日志、隐私设置。

### 5.3 关键接口行为

入库成功返回 201 与 `planId`、`versionNo`、`reviewId`、`planHash`；重复包返回 200 与 `duplicate: true`；版本冲突返回 409 与 `headVersion`、`baseHash`、差异摘要；契约或校验失败返回 422 与 `code`、`message`、`details`、`traceId`；未登录 401、越权 403、过大 413、类型不符 415、限流 429。

分页统一使用 `page`、`pageSize`、`total`；时间统一 ISO 8601 带时区；错误响应不返回堆栈与服务器路径。

### 5.5 错误码

| 错误码 | 含义 | 使用场景 |
|---|---|---|
| AUTH_REQUIRED | 未登录 | 无会话访问业务接口 |
| FORBIDDEN | 无权限 | 越权访问他人资源或管理员接口 |
| NOT_FOUND | 不存在 | id 无效或已软删除 |
| CONFLICT_STALE | 版本冲突 | `baseHash` 与头版本不一致 |
| HASH_MISMATCH | 哈希不符 | 教案内容被篡改或传输损坏 |
| SCHEMA_UNSUPPORTED | 版本不支持 | 未知 `schemaVersion`/`rubricVersion` |
| STRUCTURE_INVALID | 结构校验失败 | 复校未通过，附 issue 列表 |
| REPORT_INCONSISTENT | 报告不一致 | 报告哈希、轮次、状态、放行与教案不符 |
| MEDIA_MISSING | 媒体缺失 | 文件缺失或哈希不符 |
| PAYLOAD_REJECTED | 包内容被拒 | zip 条目含 `..`、绝对路径、符号链接或非白名单文件 |
| PAYLOAD_TOO_LARGE | 请求过大 | 单包超过 50 MB |
| UNSUPPORTED_MEDIA | 媒体类型不支持 | 上传内容不是 zip 或类型不符（HTTP 415） |
| RATE_LIMITED | 触发限流 | 登录或导入过于频繁 |
| INTERNAL | 服务端错误 | 未预期异常，附 `traceId` |

### 7.3 关键负例

1. 篡改教案任意字段后上传，必须 422 且不落库。

4. `waived` 问题没有对应放行记录，必须拒收。
5. 未知 `schemaVersion`/`rubricVersion`，必须拒收并列出支持版本。
6. zip 内路径包含 `..`、绝对路径或软链接，必须拒绝。
7. 教师改 URL 读取他人教案，必须 403 且写审计。
8. 离线修改后基于旧版本上传，必须 409 并给出差异。
9. 同一契约包并发提交，只能产生一个版本。
10. 导出时门禁不通过，不得产生 DOCX。

## 9 风险与假设

| 风险 | 影响 | 应对 |
|---|---|---|
| 双端范围膨胀 | 毕设延期 | MVP 锁定六块 P0 功能，P1 按周验收，P2 可裁剪 |
| 契约漂移 | 两端数据无法互认 | 契约版本化 + 黄金测试 + 未知版本拒收 |
| SQLite 并发写 | 入库失败或数据错乱 | 单写队列 + WAL + 重试；压测 20 并发 |
| 上传与路径安全 | 服务器被写入恶意文件 | zip 白名单、路径规范化、大小与类型限制 |
| 教师接受度低 | 任务完成率不达标 | 先在教研组试点，按 SUS 反馈改页面 |
| 插件端 P0 未完成 | 平台复校放大不一致 | 平台上线前先完成插件端 P0；历史数据标 `legacy` |

**关键假设**

1. 平台端为新建，仓库当前没有 B/S 代码；本文档按新建需求写。
2. 后端采用 Python，直接复用插件端校验与导出脚本；若换语言需通过跨语言黄金测试。
3. 平台端 v1.0 不做在线编辑，修订在插件端完成后上传新版本。
4. 教师放行仍在插件端完成，平台端只读展示，避免两套放行逻辑。
5. 不采集学生个人信息；班级仅用于归属与筛选。
6. 校内单机部署，不接公网，不做多租户。
