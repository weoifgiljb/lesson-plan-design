# 校标教案双端平台 测试用例

> **测准声明**：插件端以仓库 `ecbdf49` 的实际实现为唯一功能基线，需求文档降为对照；平台端尚未实现，其用例依据《功能优化需求-BS平台端》v1.0 编写，属文档模式。代码级证据（`文件:行`、缺陷、文档偏离）统一放文件末尾附录，不写进用例正文。
>
> **功能简介**：插件/技能端在教师已有的 Agent 宿主中完成教案起草、结构校验、对抗审校与 Word 导出；B/S 平台端负责契约复校入库、版本与证据台账、批量导出、统计与权限审计。两端以教案 JSON、审查报告与 `planHash` 衔接。
>
> **角色**：任课教师 → 生成与上传教案、查看本人审查、发起导出；教研组长 → 查看本组教案与统计、批量导出；系统管理员 → 用户、样例、引擎、审计与备份。

**术语表**

| 术语 | 中文名 | 说明 |
|---|---|---|
| 契约包 | Contract Package | 一次同步提交的 zip：manifest、教案 JSON、审查报告、可选 DOCX 与媒体 |
| planHash | 教案哈希 | 教案规范化 JSON 的 SHA-256，用于失效旧报告与校验篡改 |
| baseHash | 基线哈希 | 上传时声明的"我基于哪一版修改"，用于乐观锁 |
| 审查报告 | Review Report | 记录轮次、问题、放行与审校方式的 JSON |
| 证据链 | Evidence Chain | 哈希匹配、轮次连续、放行完整、审校方式合规四项齐全 |
| 门禁 | Export Gate | 导出前同时检查结构结论与审查结论的闸门 |
| 契约复校 | Ingest Revalidation | 平台端不信任上传结论，重算哈希并重跑结构校验 |
| 八步流程 | Eight Steps | 复习导入、明确目标、知识学习、任务实施、课程考核、课堂小结、布置作业、教学反思 |

> 前置：平台端已实现 BS-01 入库管道（TODO：待 2027.03 上线）；契约包位于 `tests/fixtures/dual-end/platform/packages/`。

  - 前置条件: `valid-0201.zip` 已生成，教案为第 2 周第 1 次「一级考证辅导2」
  - 操作步骤: 1. 用教师账号登录平台 2. 进入「教案库 → 上传契约包」 3. 选择 `valid-0201.zip` 4. 提交

- **TC-01-02 篡改教案字段后入库被拒** [P0]
  - 前置条件: `tampered-title.zip` 中课题被改为「篡改课题」，包内哈希仍为原值
  - 操作步骤: 1. 进入上传契约包 2. 选择 `tampered-title.zip` 3. 提交
  - 预期结果: 入库失败，提示「教案内容哈希不符」；教案库不新增记录
  - 验证方式: 查教案表无新增；审计表记录一次拒绝及原因
- **TC-01-03 规范化等价输入哈希不变** [P1]
  - 前置条件: 同一教案两份文件：A 为原文件，B 打乱字段顺序并把中文写成转义形式

  - 预期结果: 两份哈希完全相同；B 按重复包处理，不产生新版本
  - 验证方式: 两次响应中的哈希值一致
- **TC-01-04 包内文件哈希不符** [P1]
  - 前置条件: `media-hash-mismatch.zip` 中媒体文件哈希被改为全 0，文件仍在
  - 操作步骤: 1. 上传该包 2. 提交
  - 预期结果: 入库失败，提示「媒体文件哈希不符」；无落库
  - 验证方式: 审计表拒绝记录含文件名
- **TC-01-05 未知契约版本** [P1]
  - 前置条件: `bad-schema.zip` 的教案结构版本为 99
  - 操作步骤: 1. 上传该包 2. 提交
  - 预期结果: 入库失败，提示「结构版本不支持」，并列出当前支持版本 1
  - 验证方式: 响应与审计一致
- **TC-01-06 重复包幂等** [P1]
  - 前置条件: `valid-0201.zip` 已成功入库为第 1 版
  - 操作步骤: 1. 再次上传同一 zip 2. 提交
  - 预期结果: 返回成功但标记为重复；版本数仍为 1
  - 验证方式: 教案版本表仍 1 条；审计新增一条「重复提交」
- **TC-01-07 压缩包路径穿越被拒** [P1] [安全]
  - 前置条件: `zip-slip.zip` 中含名为 `../../evil.txt` 的条目
