# 难题记录：契约类型化与前端硬编码治理

> 记录本轮（#35 / #36）踩到的坑，供后续改契约、加模型、调前端时对照。每条含"现象 → 原因 → 处置"。

## 1. `response_model` 会**静默过滤**多余字段

**现象**：认证组挂上 `response_model=TokenOut` 后，`/auth/login` 的响应里 `csrfToken` 消失，前端登录直接不可用；`/auth/me` 的 `mustChangePassword` 也没了。全量测试报错，但 422/200 状态码一切正常，只有字段少了。

**原因**：FastAPI 用 `response_model` 做序列化白名单，模型里没声明的键会被丢掉，**不会报错**。

**处置**：
- 模型字段必须与 `user_payload()` / `_item()` 的实际返回**逐字段对齐**；只为"未来可能加"的字段给默认值，不能靠"模型窄一点没关系"。
- 每加一个 `response_model`，先跑该域测试（如 `test_tasks_api.py`）再跑全量——状态码对不代表字段对。
- 认证组因此拆成 `LoginOut(TokenOut)`（多 `csrfToken`）与 `TokenOut`；`UserOut` 补 `mustChangePassword` / `group`。

## 2. `Literal[...] | None` 在 OpenAPI 里是 `anyOf`，不是 `enum`

**现象**：把 `status: str | None` 改成 `Literal[...] | None` 后，直接读 `parameter["schema"]["enum"]` 是 `None`，误以为枚举没生效。

**原因**：可空枚举会生成 `anyOf: [{enum: [...]}, {type: null}]`。

**处置**：校验时看 `schema.anyOf[0].enum`；`gen_frontend_types.py` 能正常生成 `'draft' | ... | null`。

## 3. 枚举类型从 domain 常量派生，别手写第二份

```python
TaskStatus = Literal[tuple(sorted(task_rules.TASK_RANK))]
TaskQuadrant = Literal[tuple(sorted(task_rules.QUADRANTS))]
ReviewStatus = Literal[tuple(sorted(report_rules.ALLOWED_STATUS))]
RoleName = Literal[tuple(roles.ROLES)]
```

写成 `Literal[tuple(...)]`（Python 会把 tuple 展开）；写在 `api/schemas.py`，domain 不依赖 pydantic。

## 4. 非法枚举值以前是"静默空列表"

`GET /tasks?status=bogus` 原来走 SQL 等值查询，返回 `total=0`；改枚举后变 422。**这类语义变化必须同批改测试**（`test_tasks_api` 里那条断言就从 `total==0` 改成 `422`）。

## 5. `node_modules` 用 junction 挂进 worktree 会让闸门误报

**现象**：BA-12 报 35 条"不得写入本机绝对路径"，全部来自 `node_modules/*/README.md`。

**处置**：跑前端检查时临时挂 junction，跑完立刻 `rmdir` 再跑闸门；不要把 junction 留在工作树里。

## 6. ECharts（Canvas）不认 CSS 变量

`itemStyle.color: 'var(--lpp-primary)'` 不报错但不生效。用 `getComputedStyle(document.documentElement).getPropertyValue('--lpp-primary')` 运行时取色并缓存（见 `src/frontend/src/utils/theme.ts`）。

## 7. BC-07 的前端调用识别有历史 bug

`CALL_RE` 原来是 `client\.(get|post|put|patch|delete)\s*(?:<[^>]*>)?\s*\(`：
- 泛型嵌套（`client.get<Paged<TaskItem>>(...)`）匹配失败 → 误报"前端没调用"；
- 不识别 `client.download/upload` → 下载/上传类端点全部误报。

已修为 `(?:<[^(]*>)?` + 补 `upload|download` 并映射 GET/POST。**改这个正则会让 BC-07 的"缺失数"骤降，属误报修复，不是功能补齐。**

## 8. WAL 下 `shutil.copy2` 备份会丢事务

**现象**：库开着 WAL、写连接未 checkpoint 时复制 `app.db`，副本缺表或丢最新事务，而 repair 仍打印"已备份"并报"结构已对齐"。

**处置**：备份改用 `sqlite3` 的在线备份 API（`src.backup(dst)`）+ 打开校验（`integrity_check`、表数 > 0）；`scripts/repair_schema.py` 已改。

## 9. 迁移跳号 + `schema.sql` 重复列 = `duplicate column`

**规则**：新列只加在迁移里，`schema.sql` 不重复声明；否则 `initialize()` 在"版本号跳号的老库"上会报 `duplicate column`（0005 的 `report_sha256`、0011 的 `token_version` 都踩过）。

**另**：`repair.py` 的 `TASK_TABLE_SQL`/`TASK_COPY_SQL` 必须同步新列，否则重建后 `CREATE INDEX` 报 `no such column`。

## 10. 测试里别写死中文文案

状态名/占位语收敛到 `src/frontend/src/utils/labels.ts` 或后端 `/meta`；测试断言引用常量（`REVIEW_STATUS_LABELS.passed`）而不是 `'已通过'`，否则改文案就假红。

## 11. 顺序反了必红：先 `--update-contract`，再跑测试

**现象**：加完 `response_model` 直接跑 `index.py`，`test_snapshot_matches_application` 报 `$ref: PlanPage` 与旧的 `additionalProperties` 不一致。

**原因**：快照测试比对的是 `docs/api/openapi.v1.json`，它要等 `--update-contract` 重新生成后才更新。

**固定顺序**（每批都照这个来）：

```
1) 改 schemas / 路由挂 response_model
2) py -3 scripts/run_backend_gate.py --update-contract
3) py -3 scripts/gen_frontend_types.py      （前端类型同批）
4) py -3 src/backend/tests/index.py         （此时快照已一致）
5) py -3 scripts/run_backend_gate.py --json （0 block 才提交）
```

反过来的代价是多跑一遍全量测试，且容易误判成"模型写错了"。

## 12. 同一模型被"列表/详情"两种返回复用时，必有一个字段对不上

**现象**：`PlanVersionOut` 既用于详情（带完整 `content`）又用于版本链（只有元信息 + `status`），挂上 `response_model` 后：先报 `content 字段缺失`，补成可空后版本链测试又 `KeyError: 'status'`。

**原因**：`response_model` 只认声明过的字段，多出来的键被吞掉；两个端点返回形状不同却共用一个模型，必然顾此失彼。

**处置**（三选一，按契合度）：
1. **拆模型**：`PlanVersionDetailOut`（带 content）与 `PlanVersionSummaryOut`（带 status）——最干净；
2. **字段设默认值**：把所有可能出现的键都列出来并给默认（适用于差异很小的情况）；
3. **`model_config = ConfigDict(extra="allow")`**：保留未声明的额外键（本次采用）——能立刻止血，但类型表达力打折，属临时手段，后续应回到 1。

**判断依据**：如果两个端点的返回键集合差异 > 2 个，直接拆模型；只有 1 个可选字段才用默认值。
