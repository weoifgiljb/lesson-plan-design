## 2 排序原则

1. **先可复现**：测试基线不修，后面的“完成”都不可验证。
2. **先已上线正确性**：BS-08 的统计口径与前端体积、FR-02/03/05/10 的验收缺口优先于新功能。
3. **先 P0 运维**：OPS 的备份、恢复、防呆、迁移手册先于 P1/P2 功能。
4. **一需求一分支**：同一批次内按 FR/BS/OPS 编号拆分支，不把多个需求混在一个 PR。
5. **可裁剪**：答辩时间不足时先保“可演示 + 可恢复 + 可解释”，通知、字段级修订、管理端 UI 可后置。

## 5 完成定义（DoD）

每个 OPT 条目完成，必须同时满足：

1. 代码 + 正常/边界/错误用例；
2. 相关套件通过；涉及 `src/backend`、`src/frontend/src/api`、`docs/api` 时 `run_backend_gate.py` 无 block、`run_all_tests.py` 全绿；
3. 契约变更同批更新 `contract.v1.json`、OpenAPI 快照、前端类型；
4. 更新对应 FR/BS/OPS 状态、证据、缺口与本文件状态；
5. 需求 md → docx 重建，`docs/README.md` 同步；
6. PR 写明关联的 FR/BS/OPS 与 TC 编号。

## 6 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 夹具/时间戳不可复现 | “全绿”声明失真 | OPT-02 已关闭；改夹具后跑 `run_plugin_fixtures.py`，并保持固定时间戳 |
| 解释器与依赖不一致 | 换机/答辩现场跑不起来 | doctor 检查；迁移手册写死命令 |
| 样例复核依赖教研组 | FR-13/BS-09 卡住 | 先用现有 7 份保底；15 份作为 B3 目标 |
| 契约变更跨端 | 前后端/闸门不同步 | 同批提交契约、快照、类型与用例 |
| 单人时间不足 | P2 做不完 | 按第 3 节裁剪；答辩主线是 B0—B2 |
| 快照含敏感数据 | 泄露风险 | 不入 Git、不公开、日志不打印 |
