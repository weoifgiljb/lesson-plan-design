## 0. 三个问题的结论

### 0.1 图一：为什么写死本地绝对路径

`docs/ide-setup.md` 是 Codex 的 MCP 配置示例。TOML 不会展开 `${PLUGIN_ROOT}`，编写时把本机路径直接复制了进去：

```toml
args = ["-3", "C:/Users/<user>/Desktop/<repo>/plugins/lesson-plan-design/scripts/mcp_server.py"]
```

这是**文档缺陷，不是运行必需**。它会导致：

- 其他人复制后路径不存在；
- 文档泄露本机用户名和目录结构；
- 与 `plugins/lesson-plan-design/mcp.json` 中正确的 `${PLUGIN_ROOT}` 写法不一致。

同类问题还有：

| 位置 | 情况 | 处理 |
|---|---|---|
| `docs/ide-setup.md:40` | 已跟踪的 TOML 示例写死绝对路径 | 改成 `<仓库绝对路径>` 占位，并注明 Codex 需手工替换 |
| `.cursor/mcp.json` | 本地 IDE 配置，当前未跟踪 | 加入 `.gitignore`，提供 `.cursor/mcp.example.json` |
| `scripts/regenerate_c_plans.py:6` | `ROOT` 写死 `C:\Users\...` | 改为 `Path(__file__).resolve().parents[1]` |
| `测试用例_markmap.md:13` | 测试环境说明写死仓库绝对路径 | 改成 `<仓库根目录>`，保留 Windows/Python 版本信息 |

`plugins/lesson-plan-design/mcp.json` 已经是正确写法，不需要改：

```json
"command": "py",
"args": ["-3", "${PLUGIN_ROOT}/scripts/mcp_server.py"]
```

### 0.2 图二：类型判断能不能用“枚举/映射”写

可以，而且建议这么做。这里不适合用 Python `enum.Enum`，因为要匹配的是**类型谓词**，不是固定值；用 `dict` 把 JSON Schema 类型映射到判断函数即可：

```python
def _is_integer(value) -> bool:
    return isinstance(value, int) and not isinstance(value, bool)


def _is_number(value) -> bool:
    return isinstance(value, (int, float)) and not isinstance(value, bool)


TYPE_CHECKS = {
    "object": lambda value: isinstance(value, dict),
    "integer": _is_integer,
    "number": _is_number,
    "string": lambda value: isinstance(value, str),
    "boolean": lambda value: isinstance(value, bool),
    "array": lambda value: isinstance(value, list),
}


def _type_ok(value, expected: str | None) -> bool:
    if expected is None:
        return True
    return TYPE_CHECKS.get(expected, lambda _value: True)(value)
```

好处：

- 新增类型只改表，不改 `_type_ok` 的分支链；
- `bool` 不被当成 `integer`/`number` 的规则集中在一处；
- 可以用参数化测试逐项覆盖，而不是只测其中两个分支。

### 0.3 图三：哪些是真正的“函数冗余”

需要区分“薄适配层”和“重复逻辑”：

| 位置 | 是否冗余 | 说明 |
|---|---|---|
| `mcp_server.py` 的 `call_tool` 与 `handle` | **是** | 两处都 `try/except` 包工具异常：`call_tool` 返回内容错误，`handle` 返回 JSON-RPC `-32603`；应抽一个会抛异常的 `_invoke_tool`，两个薄适配器各自只保留一个边界 |
| `lib.py` 的 `_refresh_report_status` 与 `export_gate` 的状态判断 | **是（部分）** | 同一套 `open/waived/accepted` 规则写了两遍，状态字面量在 `lib.py` 出现 7 次；应抽 `derive_review_status(findings)`，门禁只校验“声明状态 == 推导状态” |
| `lib.py` 的 `_text` 与 `export_docx.py` 的 `_meta_value` | **是（部分）** | 都在做“去空白 + 空值占位”，语义略有差异；应统一为 `clean_text(value, placeholder="")` |
| `export_docx` 与 `export_docx_result` | **否** | 前者是兼容旧调用的薄包装，后者返回自检/媒体信息；保留，但要在 docstring 标明“兼容入口” |
| `test_cli.py` 中重复的临时目录、写报告、跑子进程 | **是** | 37 处 `TemporaryDirectory`/`subprocess.run`/`save_review_report` 组合；应抽 `write_plan_with_report()`、`run_cli()` 测试夹具 |
| `docs`、`SKILL`、`hooks`、MCP 配置中的命令字符串 | **是（配置层面）** | `py -3` 已经统一，但没有一致性检查，下一次改动仍会漂移 |

## 2. 开发规范（建议纳入 `AGENTS.md` / PR 模板）

### R1 路径规范

- 已跟踪文件禁止出现 `C:\Users\...`、`/home/<user>/...`、`C:/Users/...`。
- 插件内路径用 `${PLUGIN_ROOT}`；仓库内脚本用 `Path(__file__).resolve().parents[n]`；文档用 `<仓库根目录>` 占位。
- 本地 IDE 配置（`.cursor/mcp.json`、个人 `.vscode/`）不提交；提交 `.example` 模板。
- 新增 `scripts/check_repo_hygiene.py` 扫描 `git ls-files`，命中即失败。

### R2 类型/枚举规范

- 封闭集合（JSON Schema 类型、状态、错误码、severity）用常量表/映射，不写长 if 链。
- 映射的值是**具名函数**，不用难以调试的复杂 lambda；`bool` 与 `int` 的边界单独注释。
- 新增枚举值必须同时补参数化测试和文档表格。

### R3 错误边界规范

- 业务函数只抛异常，不返回“半个错误对象”。
- 每个对外边界只允许一个 `try/except`：
  - CLI：`_cli.run_cli`；
  - MCP 内容适配：`call_tool`；
  - MCP JSON-RPC 适配：`handle`。
- 错误码集中定义，不在分支里写裸数字。

### R4 状态机规范

- 审查状态只允许一个推导函数 `derive_review_status(findings)`。
- `record_teacher_override` 调用它刷新状态；`export_gate` 调用它校验声明状态。
- 状态字面量只在常量表中出现，测试用常量，不复制字符串。

### R5 去重规范

- 同一行为出现 3 次以上，抽函数/夹具；但**不为两行代码提前抽象**。
- 薄包装层（如 `export_docx`）要写清“兼容入口”，不算重复逻辑。
- 测试数据用工厂函数；一个测试只保留与本用例相关的断言。

### R6 文件/函数体量

- 单函数建议 ≤ 50 行，嵌套 ≤ 3 层；超过时在 PR 说明理由。
- 单模块建议 ≤ 600 行；`mcp_server.py` 超过时按 `schema / dispatch / transport` 拆分。
- 重构 PR 只做一类改动，不夹带新功能。

### R7 文档/配置一致性

- 命令、字段、状态、错误码只在“单一来源”维护；README/SKILL/hooks/MCP 由测试或生成脚本校验。
- 契约变更（JSON 字段、状态、错误码）同批更新测试、样例和需求文档。

### R8 测试规范

- 新功能必须带用例；修 bug 先补失败用例。
- 每个测试文件至少覆盖：正常、边界、错误、契约四类中的相关项。
- 测试之间不共享可变全局状态；临时目录用上下文管理器。
- `scripts/run_all_tests.py` 是唯一全量入口；提交前必须 7/7。

### R9 提交/评审规范

- 提交信息沿用 `<type>(<id>): <摘要>`；重构用 `refactor:`，不伪装成 `feat`。
- PR 描述写：改了什么、没改什么、如何验证、风险。
- 评审清单增加：绝对路径、重复分支、重复 try、重复状态判断、测试夹具复用。

### 4.2 类型：从 if 链到映射

见 0.2。测试用 `subTest` 遍历：

```python
for expected, good, bad in [
    ("integer", 2, True),
    ("integer", 2.0, False),
    ("number", 2.0, False),
    ("boolean", True, 1),
]:
    with self.subTest(expected=expected, value=good):
        self.assertTrue(_type_ok(good, expected))
    with self.subTest(expected=expected, value=bad):
        self.assertFalse(_type_ok(bad, expected))
```

### 4.3 MCP：一个会抛异常的核心 + 两个薄适配器

```python
class ToolError(Exception):
    def __init__(self, code: str, message: str, hint: str = ""):
        ...


def invoke_tool(name: str, args: dict) -> dict:
    # 只做业务；未知工具/参数错误抛 ToolError
    ...


def call_tool(name: str, args: dict) -> dict:
    try:
        return invoke_tool(name, args)
    except ToolError as exc:
        return _result(dump({"ok": False, "error": {...}}))


def handle(msg: dict) -> dict | None:
    ...
    try:
        result = invoke_tool(name, args)
    except ToolError as exc:
        return _jsonrpc_error(mid, INTERNAL_ERROR, "工具执行失败", {...})
```

这样“内容错误”和“JSON-RPC 错误”仍是两套协议，但业务异常只定义一次。

### 4.4 状态：一个推导函数

```python
def derive_review_status(findings: list[dict]) -> str:
    if any(item.get("status") == "open" for item in findings):
        return "needs_repair"
    if any(item.get("severity") in BLOCKING_SEVERITIES and item.get("status") == "waived" for item in findings):
        return "passed_with_override"
    if any(item.get("severity") == "minor" and item.get("status") == "accepted" for item in findings):
        return "passed_with_accepted_minor"
    return "passed"
```

`record_teacher_override` 用它刷新；`export_gate` 用它和 `report["status"]` 对比。
